12 · Simulated Data Profiling: Findings

SIMULATED DATA NOTICE. Every number below that describes data comes from fictional datasets (supplied by VELOOP for this task, or generated by the analyst and labelled "SIMULATED DATA — CREATED FOR ANALYTICAL TESTING"). None of it describes actual VELOOP users, earnings, withdrawals, revenue, retention, conversion or performance.

Workbook: 12_Simulated_Data_Profiling.xlsx. It is produced by scripts/profile_data.py.

The most important finding: the supplied workbook contains only Users data

The brief (sections 16 and 28) expects eight sheets: Users, Task Activity, Rewards, Wallet, Withdrawals, Referrals, Feature Events and Messy Data. The supplied VELoop_Rewards_Data_01.xlsx contains Users_1000_Clean (1000 rows × 27 columns), Users_Messy_Audit (1008 × 28), a 25-row Data_Dictionary, Synthetic_Summary and README_Data_Status.

What was done about it: 1. The supplied sheets were profiled and audited in full. Every Synthetic_Summary metric reconciles exactly: all 8 of 8 match. 2. Under section 28 ("they may also create additional simulated data if required"), the missing datasets were generated with a fixed seed, anchored to the 1,000 supplied user IDs, and every row was labelled SIMULATED DATA — CREATED FOR ANALYTICAL TESTING. The method is documented in data/simulated/GENERATION_METHODOLOGY.md. 3. J2 records that the relationship tests on supplied data are NOT TESTABLE (6 tests), because the child tables do not exist. Results on generated data show the model works. They do not show that VELOOP data is clean.

Missing cells in analyst-generated tables are mostly conditional blanks by design: for example, completed_at_utc is empty for abandoned tasks and referred_user_id is empty until registration. They are not defects. The per-column profile in the workbook separates them.

Notes on generated volumes compared with the brief's approximate targets: Rewards 5,651 (target about 5,000) and Wallet 6,656 (target about 3,500). The wallet is larger because the ledger must hold one row for every balance movement: each credited VE/GEM reward, each reversal and correction, each redemption and refund, and each exchange pair. Cutting rows to hit 3,500 would break the reconciliation the model is meant to prove.

Of the 14 KPIs tested against the supplied structure, 1 can be computed fully, 4 only partially (snapshot status without timestamps), and 9 not at all. The supplied structure is a user snapshot, so it cannot support any time-based engagement, money or referral KPI. That is the strongest argument for the event and transaction model in deliverables 08 to 10.

How the supplied activity flags were derived (reverse-engineered)

is_active_7d and is_active_30d reproduce with 0 mismatches only when computed as "last_login_datetime ≥ 2026-09-15 00:00 minus 7/30 days". Any other reference moment gives mismatches (14 and 16 at 2026-09-15 23:59:59). days_since_registration uses the same reference, so users who registered later on 15 Sep get negative values (DQ-C05). Both flags are login-based, while the proposed DAU is based on qualifying activity. The two definitions will not match, and both are recorded in the change log.

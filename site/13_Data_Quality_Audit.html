How detection was kept honest

Detection uses rules only. The clean sheet and the injection log are opened after detection, purely to score the rules:

  • Supplied Users_Messy_Audit: the rules found 12 of 12 cells that differ from the clean sheet, plus 8 of 8 duplicate rows, with 0 extra and 0 missed.
  • Analyst-generated Messy_Data (522 rows): 90 of 90 injected defects detected, 0 missed, 0 false positives, across all 14 check types the brief lists.

Earlier runs of this audit caught two bugs in the analyst's own generator: withdrawals whose processing time fell after their final time, and capitalisation defects that produced invalid statuses. Both were fixed. The ordering checks S09–S13 in deliverable 12 now guard against them.

Issues found in the supplied "clean" sheet

The supplied clean sheet still has logical problems that a column-by-column check would miss:

  • DQ-C01: 91 users have active_days = 0 but lifetime_sessions > 0.
  • DQ-C02: 30 users have a last login but 0 sessions. DQ-C03: 72 have sessions but no login (all of them Pending Verification).
  • DQ-C04: 34 users are opted into marketing while their consent is still Pending. This is a governance conflict.
  • DQ-C05: 4 negative days_since_registration values. DQ-C06: 4 last logins after the stated period end.
  • DQ-C10: the analytics dataset contains direct identifiers (name, email) and sensitive attributes (exact age, gender, city).

Work Package L: Data Quality Control Framework

Each rule is placed at the earliest layer of Application → Data Collection → Raw Data → Transformation → Analytics Layer → Dashboard where it can stop the defect. Fixing data at the source is cheaper than cleaning it later.

rule_id rule layer check_logic action_on_failure owner catches
QC-01 ID validation Application; Data Collection IDs generated server-side; non-null; match agreed pattern; event_id generated once and reused on retry. Reject event at collection; alert engineering. Engineering DQ-M02, DQ-U01
